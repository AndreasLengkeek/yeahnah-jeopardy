# Daily Double

Status: ready-for-agent

## Problem Statement

Every Tile today behaves identically: whoever Buzzes first gets to answer for its printed Value. That flattens the game compared to real Jeopardy, where one Tile per board is a secret Daily Double — no race to Buzz, just one Player staking their own Wager on a Clue only they'll get to answer. Without it, the Board has no moment of individual risk-taking, and no comeback mechanic for a Player who's fallen behind.

## Solution

Hide exactly one random Tile per Board as the Daily Double, kept secret from everyone — including the Host — until it's selected. Once selected, the Host designates which joined Player wagers (any Player, connected or not); that Player submits their own Wager, between $5 and the greater of their current score or the board's static $500 top Value, from their own device. The Host then judges their spoken answer same as any other Clue — correct adds the Wager to their score, incorrect subtracts it — and the Answer auto-reveals either way, since nobody else ever gets a turn at this Clue.

## User Stories

1. As a Host, I want exactly one Tile per Board to secretly be the Daily Double, so that the game has one moment of individual risk-taking per playthrough.
2. As a Host, I want the Daily Double's identity assigned at random when the Board is built, so that I can't plan around it and the surprise is genuine.
3. As a Host, I want the Daily Double Tile to look identical to every other Tile of its Value before selection, so that neither I nor anyone else can tell which Tile it is in advance.
4. As a Host, I want to not know which Tile is the Daily Double until I select it, so that the suspense matches the real show and I can't accidentally telegraph it.
5. As a Host, when I select the Daily Double Tile, I want to be told immediately that it's a Daily Double, so that I know to designate a wagering Player instead of waiting for a Buzz.
6. As a Host, I want to designate which joined Player wagers on the Daily Double, so that the game has an answer to "who wagers" even though I — not Players — select every Tile.
7. As a Host, I want every joined Player available to designate, regardless of whether their device is currently connected, so that I'm not blocked from picking the right Player just because their connection dropped.
8. As a Host, I want to redesignate a different Player if I tap the wrong name, as long as they haven't submitted a Wager yet, so that a simple mis-click doesn't lock in the wrong Player.
9. As a Host, I want my redesignation to be blocked once the designated Player has submitted a Wager, so that a Wager already in flight can't be silently reassigned mid-flight.
10. As a Player, once the Host designates me to wager, I want to see a Wager-entry control on my own device, so that I can stake my own amount without the Host typing it for me.
11. As a Player, I want to see the minimum ($5) and maximum I'm allowed to Wager before I submit, so that I don't have to guess and get rejected.
12. As a Player whose score is above the board's $500 top Value, I want my maximum Wager to equal my current score, so that I can go all-in when I'm ahead.
13. As a Player whose score is at or below the board's $500 top Value (including exactly $0 or negative), I want my maximum Wager to be $500, so that a Daily Double drawn early in the game — before I've won or lost anything — is still meaningful to play.
14. As a Player, I want my Wager submission rejected outright (not silently adjusted) if it's outside the allowed $5–max range, so that I always know exactly what amount was recorded, never a value the server quietly rewrote.
15. As a Player, once I've submitted my Wager, I want it to be final, so that there's no back-and-forth changing my stake after I've committed.
16. As a Player who is not the designated wagerer, I want to see a banner naming who is currently wagering (reusing the existing Buzz-banner swap), so that I understand why the Clue Card looks "stuck" and I'm not expected to Buzz.
17. As a Player who is not the designated wagerer, I want to never see a Buzz control while a Daily Double is being wagered on, so that I don't waste a tap trying to compete for a Clue I was never eligible for.
18. As a Board viewer, I want to see the same wagering-Player banner as Players do, so that the shared display always explains the current state of play.
19. As a Host, once the designated Player's Wager is submitted, I want to see the normal Correct/Incorrect judging controls, so that judging a Daily Double feels like judging any other Clue.
20. As a Host, I want the Clue's scoring to use the submitted Wager instead of the Tile's printed Value, so that the actual stakes reflect what the Player chose, not what's printed on the Tile.
21. As a Host, when I judge the Daily Double correct, I want the wagering Player's score to increase by their Wager, so that a successful gamble pays off exactly as staked.
22. As a Host, when I judge the Daily Double incorrect, I want the wagering Player's score to decrease by their Wager, so that a failed gamble costs exactly as staked.
23. As a Host, I want the Answer to auto-reveal the instant I judge a Daily Double — correct or incorrect — so that I never need a separate Reveal click regardless of outcome, unlike a normal wrong Buzz which keeps the Answer hidden for the next Player.
24. As a Host, I want the Daily Double Clue to become immediately closable the instant I've judged it, with no re-attempt loop for any other Player, so that closing feels the same one-step motion as any other resolved Clue.
25. As a Board viewer or Player, I want the Daily Double Tile shown as a normal used, emptied Tile once its Clue closes, so that there's no lingering visual trace of which Tile it was after the fact.
26. As a Host, I want a fresh Board rebuild (Reset Game, or returning to Board Setup and reopening the Lobby) to draw a new random Daily Double Tile, so that replaying the same Board Config doesn't put the Daily Double in the same place every time.

## Implementation Decisions

- **`ActiveClue` gains Daily Double fields** in `shared/src/types.ts`: `isDailyDouble: boolean`, `wageringPlayerId: string | null`, `wager: number | null`. `Tile` itself gains nothing — the Daily Double's identity lives only on the `ActiveClue` once selected, and is never stored on `Category`/`Tile` at all; instead, the random pick happens at `selectTile` time (see below), so the Board's own data never encodes which Tile is secretly a Daily Double.
- **Random assignment mechanism**: rather than pre-marking one Tile when the Board is built, the simplest correct implementation is to pick the Daily Double's `(categoryIndex, tileIndex)` once, at the same moment `buildBoard` runs (Lobby opens / Board rebuilds), and carry that coordinate in `GameState` as a Host-invisible value (not exposed via `viewForRole` to any role, including the Host's own broadcast state — it must only ever surface through `activeClue.isDailyDouble` once that specific Tile is selected). `applySelectTile` checks the selected coordinate against this stored pick to set `isDailyDouble` on the new `ActiveClue`. Re-picked fresh on every `buildBoard` call (`openLobby` and `resetGame`), so replaying a Board Config draws a new Daily Double each time (user story 26).
- **New `GameAction`s** in `shared/src/types.ts`, handled in `shared/src/gameEngine.ts`'s `applyAction`:
  - `designateWagerer { playerId: string }`: valid only while `activeClue.isDailyDouble` is true and no Wager has yet been submitted (`activeClue.wager === null`). Sets `activeClue.wageringPlayerId` to any Player in `state.players` regardless of `connected` status (user story 7). Overwrites any prior designation — this is how redesignation (user story 8) works, and it naturally no-ops once `wager !== null` (user story 9), matching the reducer's existing reject-by-no-op convention.
  - `submitWager { playerId: string; amount: number }`: valid only if `playerId === activeClue.wageringPlayerId`, `activeClue.wager === null`, and `amount` falls within `[5, maxWagerFor(player.score)]` inclusive, where `maxWagerFor(score) = score > 500 ? score : 500`. Any submission outside that range, or from anyone other than the designated Player, or after a Wager already exists, is a no-op (user story 14) — the reducer never clamps. On success, sets `activeClue.wager = amount`, final from that point on (user story 15).
- **`applyJudge` changes**: when `activeClue.isDailyDouble` is true, the value added to/subtracted from the wagering Player's score is `activeClue.wager` instead of the Tile's printed Value. Both outcomes (correct and incorrect) set `revealed: true` in the same reducer step — extending ADR-0007's auto-reveal to the incorrect path specifically for Daily Double Clues (see ADR-0011), since there is no `excludedPlayerIds` loop to reopen for anyone else. `wageringPlayerId` plays the same structural role `buzzedPlayerId` plays for a normal Clue (the reducer treats "who currently must be judged" the same way — a null-check gate before judging is possible), so `applyJudge`'s existing null-check gating extends naturally to also require a submitted Wager for a Daily Double.
- **`canCloseClue` changes**: for a Daily Double Clue, once judged (either outcome, which per the above always sets `revealed: true`), it's immediately closable — the existing `clue.revealed → true` closable branch already covers this without further change, since both Daily Double outcomes now revealed. No separate `excludedPlayerIds` accumulation ever happens for a Daily Double Clue (no Buzz race exists for it at all), so the existing "no one buzzed yet" / "everyone excluded" branches simply never apply to it.
- **`applyBuzz` changes**: a `buzz` action is a no-op whenever `activeClue.isDailyDouble` is true — there is no Buzz race for a Daily Double under any circumstance, matching user story 17.
- **Server wiring** in `server/src/server.ts`: two new socket events, `designateWagerer` and `submitWager`, dispatched 1:1 exactly like every existing action (`socket.on("designateWagerer", (playerId: string) => dispatch({ type: "designateWagerer", playerId }))`, similarly for `submitWager`).
- **`viewForRole` (`shared/src/gameView.ts`)**: no change needed beyond what already exists — `isDailyDouble`, `wageringPlayerId`, and `wager` all live on `activeClue`, which is already redacted/passed through per role the same way `buzzedPlayerId` is today. The pre-selection random Daily Double coordinate (see above) must never be attached to `GameState` in a way `viewForRole` would expose to any role; it needs to live somewhere the view layer can't reach it at all (e.g. module-private server state alongside `state`, or a field explicitly stripped for every role including host in `viewForRole`) — the implementer should pick whichever shape keeps this invisible without changing `GameState`'s existing broadcast shape for every other action.
- **`ActiveClueDetails` (`client/src/activeClue.ts`)** gains `isDailyDouble: boolean`, `wageringPlayer: Player | null` (resolved via the existing `resolvePlayer` helper, same as `buzzedPlayer`/`correctPlayer`), and `wager: number | null`.
- **`ActiveClue.tsx`** treats a wagering Player exactly like a buzzed Player for the banner-swap/hide-clue-text behavior (reusing `hideClueOnBuzz`'s mechanism, generalized to "hide clue text while someone holds the Buzz *or* is the designated wagerer and hasn't submitted yet"), with copy along the lines of "`<PlayerIdentity>` is wagering…". Once `wager !== null`, the header's `$<value>` display shows the submitted Wager instead of the Tile's printed Value for a Daily Double Clue.
- **`HostPage.tsx`** gains a "pick who wagers" control, shown whenever `activeClue.isDailyDouble && activeClue.wager === null` — a simple list of all Players (per user story 7, connection status doesn't filter this list) the Host taps to emit `designateWagerer`; re-tappable up until a Wager lands. Once `wageringPlayerId` is set, the Host's footer waits (no Correct/Incorrect yet) until `wager !== null`, at which point the existing Correct/Incorrect footer (`hostFooter`) renders unchanged — it already keys off "is there someone to judge," which for a Daily Double becomes "is there a submitted Wager."
- **`JoinPage.tsx`** gains a Wager-entry control, shown to a Player exactly when `activeClue?.wageringPlayerId === playerId && activeClue.wager === null` — a numeric input bounded by the min ($5) and the max computed from that Player's own current score (`score > 500 ? score : 500`), displayed to the Player before they submit (user story 11), emitting `submitWager` on confirm. The existing Buzz button is hidden/disabled entirely whenever `activeClue?.isDailyDouble` is true (user story 17), replacing today's `canBuzz` gate with an additional `!activeClue.isDailyDouble` check.

## Testing Decisions

Tests exercise external behavior (state in/out, or rendered output), never internals — matching the existing suite's style throughout.

- **`shared/src/gameEngine.test.ts`** (extend): plain `GameState` in/out, no mocks, same pattern as existing describe blocks. New coverage:
  - Selecting the pre-picked coordinate sets `activeClue.isDailyDouble = true`; every other Tile selection leaves it `false`.
  - `designateWagerer` sets `wageringPlayerId` to any Player regardless of `connected`; is a no-op for a non-Daily-Double Clue; is a no-op once a Wager already exists; overwrites a prior designation (redesignation) right up until a Wager lands.
  - `submitWager` accepts amounts from $5 up to `score` (when `score > 500`) or up to $500 (when `score <= 500`, including exactly `0` and negative scores); rejects (no-op, doesn't mutate `activeClue.wager`) amounts below $5, above the computed max, from a non-designated Player, or once a Wager already exists.
  - `judge` on a Daily Double Clue: correct adds `wager` (not the Tile's Value) to the wagering Player's score and sets `revealed: true`; incorrect subtracts `wager` and *also* sets `revealed: true` (diverging from the normal wrong-Buzz path, which leaves `revealed: false`); is blocked (no-op) until a Wager has been submitted.
  - `canCloseClue` returns `true` immediately after either Daily Double judgment, with no dependency on `excludedPlayerIds`.
  - `buzz` is a no-op whenever `activeClue.isDailyDouble` is true, regardless of who calls it.
  - A `resetGame`/`openLobby` rebuild draws a fresh random Daily Double coordinate (assert indirectly: across many rebuilds, the resulting Daily Double Tile position varies — or, if the implementer exposes a seam for it, assert the underlying pick function is called fresh each rebuild).
- **`server/src/server.test.ts`** (extend): existing real socket.io round-trip pattern (`createGameServer`, connect real sockets). New coverage: emitting `designateWagerer` and `submitWager` each produce a broadcast state reflecting the change, following the same 1:1 wiring assertion style already used for `judge`/`reveal`/`closeClue`. Also assert that no broadcast state — to any role, including `"host"` — ever exposes which Tile is secretly the Daily Double before it's selected.
- **`client/src/activeClue.test.ts`** (extend): plain function in/out, same pattern as existing cases. New coverage: `resolveActiveClue` surfaces `isDailyDouble`, `wageringPlayer` (resolved the same way `buzzedPlayer` is), and `wager` correctly from a Daily Double `ActiveClue`.
- **`client/src/components/ActiveClue.test.tsx`** (extend): existing render-with-props/assert-output pattern. New coverage: while a Player is designated but hasn't wagered, the Clue text is hidden behind a wagering banner naming them (same mechanism as the existing Buzz-banner test); once a Wager is present, the header shows the Wager amount instead of the Tile's Value.
- **Out of unit-test scope**: `HostPage.tsx`'s designate-Player list and `JoinPage.tsx`'s Wager-entry control are plain route wiring with no existing test coverage precedent (neither file has a test today; the existing Buzz button and judge buttons aren't unit-tested either) — verify these manually via the `run-yeahnah-jeopardy` skill instead of adding new test files for them.

## Out of Scope

- A dedicated Board Sound cue for the Daily Double — reuses the existing Buzz-landing/Judge-outcome cues (a submitted Wager is treated as the Daily-Double equivalent of a Buzz landing).
- Host-configurable count or explicit Host placement of the Daily Double — always exactly one per Board, always randomly assigned.
- Any visibility of the Daily Double's identity ahead of selection, to any role — it is a genuine surprise every time, including to the Host.
- Withholding the Daily Double's Clue text pending the Wager — Clue text shows immediately on selection exactly like any other Tile; only the Answer stays gated behind judging, as it already does for every Clue.
- Any UI affordance for the Host to manually trigger Reveal on a Daily Double — both judged outcomes already auto-reveal, so the existing Reveal button/action is simply never reachable for a Daily Double Clue (no new guard needed beyond the existing `revealed` no-op check).
- A record of which Tile was the Daily Double surviving Clue close — once resolved, its Tile looks exactly like any other used Tile, and `ActiveClue` (including `isDailyDouble`/`wageringPlayerId`/`wager`) is cleared to `null` on close same as today.

## Further Notes

- `CONTEXT.md` already has **Daily Double** and **Wager** glossary entries (added during the grilling session that produced this spec) — no further glossary work needed.
- ADR-0009 (Host designates the wagerer), ADR-0010 (static $500 wager ceiling), and ADR-0011 (Daily Double always auto-reveals) already capture the three most non-obvious decisions baked into this spec — implementers should read those alongside this spec, not just this file in isolation.
- The exact mechanism for keeping the random Daily Double coordinate invisible to `viewForRole` (module-private server state vs. a stripped `GameState` field) is left to the implementer's judgment — the one hard constraint is that no broadcast to any role, including `"host"`, may ever reveal it before that specific Tile is selected.
